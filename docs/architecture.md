# Architecture

This document describes the target architecture of ROSII Management and what is
actually implemented at the current stage. Anything marked *planned* does not exist
in the code yet.

## Database architecture

```text
ROSII Desktop
      |
      | REST API
      v
Spring Boot
      |
      v
PostgreSQL
```

- **PostgreSQL** is the central database. It is the single authority for business
  data; the Spring Boot backend is the only component that talks to it.
- **SQLite** will later be used locally by the desktop application so the patronne
  can keep working offline (*planned*).
- **SQLite synchronization is NOT implemented yet.** Once it exists (offline-first
  push/pull, optimistic versioning, conflict handling), PostgreSQL remains the
  central authority: the local SQLite store is a replica, never the master copy.

## Desktop application (`desktop/`)

- **Tauri 2** hosts the front end in a native window (`desktop/src-tauri`).
  The Rust side is intentionally minimal: no plugins, no custom commands yet.
- **Vite + React 19 + TypeScript (strict)** in `desktop/src`.
- **Tailwind CSS 4** via `@tailwindcss/vite`; design tokens defined in
  `src/index.css` following the shadcn/ui convention (`components.json` is present so
  `npx shadcn add <component>` works out of the box).
- **SQLite + Drizzle ORM** will be introduced when the offline data layer is built
  (*planned*).

## Backend (`backend/`)

- Base package: `mg.rosii.management`.
- Spring Web, Validation, Data JPA; PostgreSQL JDBC driver on the runtime classpath.
- `GET /api/health` → `{"status":"UP"}` for liveness checks.
- All database configuration comes from environment variables
  (`DATABASE_URL`, `DATABASE_USERNAME`, `DATABASE_PASSWORD`); no credentials in code.
- **Schema management is migration-controlled (Flyway).** Migrations live in
  `src/main/resources/db/migration` and run on startup. Hibernate never creates or
  alters the schema (`ddl-auto: none`), and `FLYWAY_ENABLED=false` allows booting
  without a database for pure frontend/backend development.
- Database conventions (UUID ids, audit timestamps, optimistic versioning, soft
  deletion, naming) are documented in [database-conventions.md](database-conventions.md).

## Database conventions (summary)

| Topic              | Convention                                                        |
| ------------------ | ----------------------------------------------------------------- |
| Identifiers        | UUID primary keys, generated by the application (`@UuidGenerator`) |
| Audit timestamps   | `created_at` / `updated_at`, UTC, via Spring Data JPA auditing     |
| Optimistic locking | `version` field with `@Version` on synchronizable entities         |
| Soft deletion      | `deleted_at` timestamp, explicit filtering, no global filter       |
| Naming             | `snake_case` tables/columns, Flyway `V<n>__<description>.sql`      |

Details and code templates: [database-conventions.md](database-conventions.md).

## Integration tests

Tests that need real PostgreSQL use Testcontainers (PostgreSQL container +
`@ServiceConnection`). They skip automatically on machines without Docker, so
`./gradlew test` works everywhere. A larger integration-test framework is
deliberately postponed.

## Synchronization (*planned*)

The desktop app will remain fully usable offline against SQLite and synchronize with
the central PostgreSQL database:

- push/pull synchronization endpoints
- `operationId` idempotency for retried operations
- `changeSequence` cursor to track what has been pulled
- optimistic versioning on entities
- `SyncConflict` and `ChangeLog` / `AuditLog` records

None of this is implemented yet.
