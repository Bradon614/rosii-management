# Database Conventions

Conventions every ROSII Management database change must follow. They exist so that
future business entities, migrations, and the offline synchronization layer (planned)
stay consistent.

Implemented in Feature 02. **No business entities exist yet** — the snippets below are
templates for future features, not existing code.

## Naming conventions (PostgreSQL)

| Item               | Convention                | Example                     |
| ------------------ | ------------------------- | --------------------------- |
| Tables             | `snake_case`, plural-free | `client`, `payment`         |
| Columns            | `snake_case`              | `reference_number`          |
| Primary key        | `id` (uuid)               | `id uuid PRIMARY KEY`       |
| Creation timestamp | `created_at`              | `created_at timestamptz`    |
| Update timestamp   | `updated_at`              | `updated_at timestamptz`    |
| Soft delete        | `deleted_at`              | `deleted_at timestamptz`    |
| Optimistic version | `version`                 | `version bigint NOT NULL`   |
| Foreign keys       | `<entity>_id`             | `client_id`                 |
| Migrations         | `V<n>__<snake_case_description>.sql` | `V2__create_client.sql` |

Java-side, the default Hibernate naming strategy
(`CamelCaseToUnderscoresNamingStrategy`, set explicitly in `application.yml`) converts
camelCase fields to snake_case columns, so `@Column` annotations are usually
unnecessary for simple names.

## UUID primary keys

Business entities use `java.util.UUID` primary keys.

- IDs are generated by the **application/backend** (`@UuidGenerator` from Hibernate),
  never by the database and never with sequences/auto-increment.
- Column type is PostgreSQL native `uuid`.
- Rationale: ids must be creatable offline on the desktop (SQLite) and later
  synchronized to PostgreSQL without collisions.

Template for future entities:

```java
@Entity
@Table(name = "example")
@EntityListeners(AuditingEntityListener.class)
public class Example {

    @Id
    @UuidGenerator
    @Column(nullable = false, updatable = false)
    private UUID id;

    // ...
}
```

Do **not** add a generic abstract base entity for this; each entity declares its own
fields so every mapping stays explicit.

## Audit timestamps

`createdAt` / `updatedAt` are filled by Spring Data JPA auditing
(`JpaAuditingConfig`), always in **UTC**:

```java
@CreatedDate
@Column(nullable = false, updatable = false)
private OffsetDateTime createdAt;

@LastModifiedDate
@Column(nullable = false)
private OffsetDateTime updatedAt;
```

- Use `OffsetDateTime`; the database column type is `timestamptz`.
- No database triggers: the application is the single writer (matches the future
  SQLite local store, which has no trigger parity).

## Optimistic locking (for offline synchronization)

Entities whose changes must synchronize carry a `version` field with JPA optimistic
locking:

```java
@Version
@Column(nullable = false)
private long version;
```

Hibernate increments it on every update and rejects concurrent stale writes
(`OptimisticLockException`). The future push/pull synchronization (planned, not
implemented) will use this version for conflict detection.

## Soft deletion

Important business entities (clients, demands, projects, payments, reservations, ...)
will use soft deletion so deletion can synchronize between devices:

```java
@Column
private OffsetDateTime deletedAt;
```

- `deletedAt == null` means "not deleted".
- Repositories of soft-deletable entities must filter deleted rows explicitly
  (`WHERE deleted_at IS NULL`) — do **not** rely on a global Hibernate filter.
- Hard delete (`DELETE`) remains reserved for technical data.
- The actual implementation arrives with the relevant business entity, not before.

## Migration strategy (Flyway)

- The schema is owned by Flyway (`backend/src/main/resources/db/migration`).
  Hibernate never creates, alters, or drops schema: `spring.jpa.hibernate.ddl-auto=none`.
- One migration per cohesive change, applied in order, never edited after being
  committed (fix forward with a new migration).
- Migrations run on application startup; set `FLYWAY_ENABLED=false` only to develop
  the frontend/backend UI without a database.

## Integration tests

Integration tests that need PostgreSQL use Testcontainers
(`PostgresDatabaseConnectionTest`). They skip automatically on machines without
Docker; CI machines with Docker run them. Heavy integration-test infrastructure is
deliberately postponed.
